# Dashboard tickets

This repository contains the ticket views, routes, interface, data-access layer and ticket-specific Django models for the [CCI Django dashboard](https://github.com/CCI-GU-Sweden/Dashboard-django). It is not a standalone application: the core owns login, shared permissions and audit.

The package uses core user and audit models and existing PostgreSQL ticket tables. Its five Django models keep their historical `accounts_*` table names, which are also referenced by SQL. The paired core and module migrations transfer Django model state without changing those tables, verify the required tables/columns exist, and move existing content type records without changing their IDs or linked permissions. Conflicting content types stop migration for review. Run these paired migrations once, with a backup and a verified rollback plan, before starting the new application; never deploy the module migration without its matching core migration. The historical core migrations still create the five empty legacy tables on a fresh database even if tickets are disabled; eliminating that dependency needs a separately reviewed migration-history strategy. Module views enforce permissions before calling the data layer. The overview scopes researcher statistics to tickets explicitly linked to that researcher.

Set `DASHBOARD_TICKETS_ENABLED=0` in the core before startup to disable ticket routes and overview. Existing ticket data and researcher permissions are retained. The image validation code uses Pillow. Existing code copyright is retained in [CORE_LICENSE](CORE_LICENSE); this repository is MIT licensed. Run frontend tests from this checkout with `node --test tests/*.test.js`.

## Database setup

1. Run the paired Django migrations first so the five legacy `accounts_*` model tables are present.
2. Run `python manage.py setup_ticket_schema` to check the four ticket/equipment tables. Add `--apply` to create the baseline only when there are no collisions. Matching complete schemas are reused; partial or structurally different objects stop for review. The new equipment catalogue is empty: add your own equipment through the dashboard. This command needs a setup identity able to create a comparison schema and objects in `public`.
3. Run `python manage.py setup_ticket_helpers` to check the two restricted deletion functions; add `--apply` to create them. This does not replace existing functions. It rejects partial or different definitions, an unexpected owner, overloads or PUBLIC execute access. The helper owner must have the required table privileges and permission to create functions and a comparison schema. Run it consistently as the same dedicated trusted owner; these are `SECURITY DEFINER` functions and must not be owned by an untrusted role. PUBLIC execute is revoked.
4. Ask the database owner to review and apply `deploy/runtime-grants.example.sql` to the intended dashboard runtime role. It grants EXECUTE on those functions but not general DELETE on the legacy ticket, image or event tables. Core identity, session and audit privileges must be handled separately.

The setup commands do not run automatically, delete data, seed CCI equipment, grant runtime privileges or validate stored data and external integrations. `deploy/` contains example setup Jobs that require reviewed image digests and environment-specific Secrets. Existing installations with a different, even compatible, schema or function owner stop for manual review; do not replace objects blindly. The separate contact-form/chat integration is not included in this package.
